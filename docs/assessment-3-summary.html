Phoneme Activity Builder: data-driven application and reporting

Reed Stelfox · Student No. 22813726 · CSE3CWA Assessment 3 · 4 October 2026
Repository: https://github.com/ReedStel/phoneme-activity-builder

The Phoneme Activity Builder lets Speech Pathology teachers build phoneme-based Wordle and Word Search activities from Australian English (HCE) phonemes and generate each one as a single playable HTML file. Assessment 1 built the interface, Assessment 2 added the database, the REST API and Docker. Assessment 3 makes the system data-driven: it now records what it does and reports on it, and that reporting is backed by end-to-end tests, load tests and accessibility audits. This document summarises the work; the video walkthrough demonstrates it.

What was added

  • Four reporting tables (one migration): page views, generation events, an audit trail of every create, update and delete, and a log of every API call. They are append-only records with no foreign keys, because deleting an activity must not delete the evidence that it existed, was used, or failed.
  • Instrumentation: the shared route wrapper times every API call and stores its method, path, status and duration; the generate endpoint records each attempt with its outcome, duration and, when it fails, the reason; writes to lists, words and activities are audited; and the browser reports how long each page stayed open using sendBeacon. All recording is fire and forget, so a metric can never slow down or break a teacher request.
  • A dashboard at /dashboard: health and database latency, alerts, eight statistics (activities stored by type, files generated, failures and success rate, average time on page, most-used activity type, API traffic and error rate, stored totals), a 14-day chart with a screen-reader table, four reporting tables and a CSV export.
  • Supporting endpoints: /api/metrics/summary (JSON), /api/metrics/report (CSV), /api/metrics/page-view (browser beacon), and a richer /health that still returns 200 OK with database status.
  • A simulated usage generator, so the reporting views have a realistic history on a fresh install or in a new container.

Load testing

One JMeter plan was run at each level against a production build. New users arrive at 50 per second and each makes the same single pass of five requests: the health check, the word lists API, the activities API, generating an activity file, and the dashboard page.

Throughput settles at about 120 requests per second from 100 users upwards, which is the capacity of one Node process in front of one SQLite file. Beyond that, arrivals exceed capacity, so requests queue and the wait grows in proportion to the queue: 318 ms at 100 users, 4.5 seconds at 1,000 and 28 seconds at 10,000. Nothing failed up to 1,000 users. At 10,000 users, 9,164 of the 9,219 failures were the dashboard page timing out at 60 seconds, because it runs about twenty aggregate queries per render, while the four API endpoints stayed between 16 and 20 seconds with single-digit error counts.

The instrumentation degraded before the application did. The server logged 198 dropped metric writes (Prisma P1008, socket timeout) while continuing to serve requests, which is the intended behaviour: recording is fire and forget, so observability is sacrificed under pressure rather than the teacher’s request. The cheapest fix by a wide margin is to cache the dashboard aggregates for a few seconds; the structural fix is PostgreSQL, which Prisma reduces to a schema and connection-string change.

Accessibility

Lighthouse scored 100, but the report still flagged a genuine defect: a phoneme key displayed “/p/ P” while announcing itself as “/p/: P (as in pond)”. That breaks WCAG 2.5.3 Label in Name (W3C, 2023), because somebody using speech control cannot say what they see. The accessible name of every key, and of the chips that remove a phoneme, now begins with the text printed on it, and a re-audit reports no failing audits at all. The daily chart also carries a screen-reader table of the same numbers, because a picture of data is no use to a person who cannot see it.

Design decisions

  • Events, not counters. A counter cannot answer when or why. Storing events allows the dashboard to show trends over a chosen window and to explain each failure.
  • Reporting must not cost the user anything. Metric writes are not awaited, and METRICS_DISABLED=1 turns them off for a clean load-test baseline.
  • Privacy. A page view stores a random per-tab identifier, a path and a duration. No personal data is collected.
  • SQLite. Keeping one file database means the whole system runs in a single container, which suits a single-teacher tool. The load results show where that choice stops scaling, and Prisma makes a move to PostgreSQL a small change.
